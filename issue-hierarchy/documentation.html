Issue Hierarchy for Jira - Documentation

Documentation

Overview

Jira shows one level of the hierarchy at a time. An epic lists its children, a story its subtasks, and nothing shows the whole piece of work, let alone work spanning projects. Multi-level hierarchy views are a Premium feature.

• See the full tree on any work item: ancestors above, children and subtasks below, with status, assignee and story points. • Each parent row rolls up done/total, story points and time logged vs estimated, and counts unestimated work instead of hiding it. • Build one hierarchy across projects from any JQL filter, which Jira cannot do natively. • A 1,000-child epic opens instantly; branches load as you open them. • Reads Jira's own parent field, so the tree matches JQL and boards. • Team-managed, company-managed and Jira Service Management projects. • Read-only, nothing stored, Runs on Atlassian.

Good to know: the app shows the hierarchy but never edits it, levels above epic are not shown, and a rollup says when it covers only the loaded part of a tree.

Highlights

  • The whole epic tree on every work item - Every work item gets a Hierarchy section: the parent and top-level epic above it, its children and subtasks below, with status, assignee and story points. No switching screens, no setup to do.

  • One hierarchy across projects, from any JQL - Release and program work rarely lives in one project. Type a JQL filter, such as a list of projects, a label or a fix version, and get one tree spanning every project you can see.

  • Epic progress you can trust - See how much of an epic is done and how many story points it holds. Large epics open instantly because branches load as you expand them, and the rollup says whether it covers all of the work.

Known limitations

  • The app is read-only. It shows hierarchy; it does not create or change links.

  • Levels above epic are not supported in v1 — Jira Standard has no parent above epic, and the app does not invent one in its own storage.

  • Rollups cover loaded descendants unless the panel says "complete".

  • Time rollups are in hours and minutes and count a story's subtasks through Jira's own Σ time fields; per-row done/total is counted by Jira for up to 60 partly loaded parents per view, and the rest say "so far" or "not counted".

  • Story points appear only where the field holds a value.

  • Issues the viewer cannot see in Jira are shown as Restricted, never silently hidden.

  • When a licence lapses the app stops showing hierarchies entirely — it does not fall back to a reduced free view.

  • In Jira Service Management the tree is only as deep as the project's issue types allow — JSM ships no epic-level type by default, so a service project is request → sub-task until an admin adds one.

Getting help

Email us and we will reply. Include the work item key, whether the project is team-managed or company-managed, and what the panel showed — a screenshot of the Hierarchy panel is usually enough. If the tree looks wrong, the issue's parent field in Jira is what the app reads, so that is the first thing to check.
