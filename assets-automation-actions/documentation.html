Delete & Append Actions for Assets in Jira — Documentation

Documentation

What this app does

Delete & Append Actions for Assets adds three actions to the Jira Automation rule editor's component picker: delete one or more Assets objects, append values to an Assets attribute, and append Assets objects to a work item's Assets field.

It exists because native Jira Automation can create and edit Assets objects but cannot delete one, and its Edit object action only overwrites or clears an attribute rather than adding to it. These three actions fill exactly that gap, requested in three open Jira Service Management Suggestions with a combined 218 votes.

Where to find it after installing

There is exactly one place these actions appear, and nothing else in Jira changes.

  • Open Project settings › Automation, create or edit a rule, and choose Add component → Other apps. The three actions — Delete Assets objects, Append to Assets attribute, Append objects to Assets field — appear in that list.

  • The first time any of the three is added to a rule, the editor asks the admin to Connect; this completes inline, in the same panel, with no separate page.

  • No admin page, no global page, no issue panel and no project settings page of its own. The app only appears inside the rule editor's component picker, and can take up to 20 minutes to appear there right after install.

Before you start

Check these four things once; every action depends on them.

  • Plan: the site runs Jira Service Management Standard, Premium or Enterprise. Assets is not part of the Free plan, and on Free each action writes a message naming the required plan to the rule audit log instead of running.

  • Assets data: at least one Assets schema with an object type and a few objects. Note one object key to test with. Keys look like ITAM-12 and are shown on every object page in Assets.

  • Permissions: the person who connects the rule must be a Jira administrator (or a project administrator for a project rule) and must be able to view and edit the Assets objects the rule touches. The actions run as that person, so they can never do more than that person could do by hand.

  • Install: after installing from the Marketplace, allow up to 20 minutes before the actions appear in the rule editor. The delay is Jira Automation caching its component list, not the app.

Step by step: your first rule in five minutes

This builds a rule you run by hand, so you can see an action work before wiring it into a real trigger. It uses Append to Assets attribute because that action removes nothing.

  1. In Jira, open a project and go to Project settings › Automation. For a rule across several projects, use Settings (cog) › System › Automation rules instead.

  2. Click Create rule.

  3. For the trigger, search for and choose Manual trigger ("Manually triggered from a work item"), then click Save (or Next in the new rule editor).

  4. Click Add component under the trigger and choose THEN: Add an action.

  5. In the action list, look under Other apps (or type "Assets" in the search box) and choose Append to Assets attribute.

  6. The first time you add one of these actions, the panel shows Connect (or "Allow access"). Click it and approve the consent screen in the same panel. This is a one-time step per user and lets the action call Assets as you.

  7. Fill in the form. Object: the test object key from Before you start, such as ITAM-12. Attribute: the name of a multi-value text or reference attribute on that object type, such as Tags, exactly as Assets shows it (a numeric attribute id also works). Values: one or more values separated by commas, such as reviewed, q4.

  8. Click Next (or Save), name the rule, for example Assets append test, and click Turn on rule.

  9. Open any work item in the project, open the Automation menu (the lightning icon) and run Assets append test.

  10. Open the rule again and click Audit log. The newest entry has one line from the action: how many values were appended and how many the attribute now holds. Open the object in Assets to see the new values next to the old ones.

Step by step: delete Assets objects

Typical use: clean up retired assets on a schedule, or remove the object a work item asked to retire.

  1. Create a rule as above. For a clean-up job use the Scheduled trigger (for example every Monday at 06:00); to test by hand use Manual trigger again.

  2. Add THEN: Add an action › Other apps › Delete Assets objects.

  3. Choose the objects in one of two ways. Objects: keys or ids separated by commas, spaces or new lines, such as ITAM-12, ITAM-13, or a smart value. AQL query: one query instead, such as objectType = "Laptop" AND Status = "Retired". Fill one of the two, not both.

  4. Max objects (1 to 50) is a safety cap: if the AQL query matches more objects than this, the action deletes nothing and says so in the audit log. Use a small number such as 5 while testing.

  5. Turn on Missing counts as done, so an object someone already deleted does not fail the run and re-running the rule is safe.

  6. Save, name and turn on the rule, then run it. The audit log line lists the keys deleted and any that were already gone. Deleted objects cannot be restored, so test with objects created for the purpose.

Step by step: add objects to a work item Assets field

Typical use: when a request is created, attach a standard set of objects to it without wiping the objects the customer already picked.

  1. Find the Assets field id: Settings (cog) › Work items › Custom fields, open the Assets field, and read the number in the page address (customFieldId=10050 means customfield_10050). The field name, such as Affected hardware, also works.

  2. Create a rule with a work item trigger such as Work item created, or Manual trigger for a first test.

  3. Add THEN: Add an action › Other apps › Append objects to Assets field.

  4. Fill in Work item with {{issue.key}} (the work item that started the rule), Assets field with the id or name from step 1, and Objects with the keys to add, such as ITAM-12 ITAM-13.

  5. Save, turn on and run the rule. Open the work item: the field holds the objects it had before plus the new ones, with no duplicates. The audit log line names the objects added.

If something does not work

Every run writes one line to the rule audit log. Find the line you see below.

  • The actions are not in the list: wait 20 minutes after installing and reload the rule editor. They are under Other apps, not among the built-in Assets actions.

  • "Assets is not set up on this site (no workspace)" or a line naming the required plan: the site is on Jira Service Management Free or has no Assets schema yet. Assets needs Standard or above.

  • "Licence inactive — … did not run": the app has no active licence or trial on this site. A Jira admin can start or renew it under Settings › Apps › Manage apps.

  • "Access to Assets API was denied" or "Work item … not found or not visible to …": the person who connected the rule cannot see or edit that object or work item. Reconnect the rule as someone who can, or grant the access in Assets.

  • "No attribute … on …; available: …" or "Input …": a name or key in the form does not match. The line lists the names that do exist.

  • "AQL matched N objects, limit M; nothing deleted": the query matched more objects than Max objects. Narrow the query or raise the cap (50 at most).

  • Anything else: email support@maxpetrov.pp.ua with the audit log line, or use the support page linked from the Marketplace listing.

Using the actions

Each action's form carries one example per field and opens with the line "Requires Jira Service Management Standard, Premium or Enterprise (Assets)." On a site without that plan, running the rule writes a message naming the requirement to the audit log instead of failing with nothing.

Delete takes a list of keys or ids, or one AQL query with a cap of 50 objects per run; an object already gone counts as deleted, so re-running a rule is safe. Append to attribute adds values to a multi-value or reference attribute without removing what is already there; a single-value attribute can only be set once this way. Append to field adds Assets objects to a work item's Assets field, keeping the ones already on it.

Every action takes smart values such as {{issue.key}} in its inputs, and every outcome — success, a licence problem, a bad input, or an Assets or Jira error — is written as one named line to the rule's audit log, with the objects or values it touched.

What it does with your data

The app runs entirely on Atlassian infrastructure and has no backend function, remote host or external permission: every call is made through Forge's own requestJira, as the person who connected the rule. It stores nothing of its own.

The full privacy policy and the security policy are separate pages; their URLs are on this app's Marketplace listing.

Known limitations

These are the limits the app was built against, written down here rather than discovered after purchase.

  • Requires Jira Service Management Standard, Premium or Enterprise. Assets is not included on JSM Free. On Free every action stops immediately with a message naming the plans it needs

  • No egress. Every call goes to the customer's own site through requestJira. No data leaves Atlassian

  • Jira only. Forge custom actions run in Jira automation, not Confluence

  • One-time connection consent. The first time someone adds an action, the editor asks them to Connect, and it completes inline. Rules copied through the REST API do not carry the connection

  • Actions run as the connected user, so that user needs Assets permissions on the target schema

  • Delete is not atomic across many objects. A run that deletes 7 of 10 reports the 7 and the 3. Assets has no bulk-delete operation

  • At most 50 objects or values per run. Larger sets use a branch

  • Attribute types in v1: Default (text, number, date, URL, email and the like) and Object reference. User, Group, Status, Confluence, Version, Project and Attachment attributes are not supported and return an error naming the attribute's type

  • Read–merge–write. Two rules appending to the same attribute in the same second can race, so each append re-reads and retries once

  • No create or edit actions: native Automation's Create object and Edit object actions already cover those

  • Actions appear in the rule picker up to 20 minutes after install

  • Single-value attributes (maximumCardinality: 1) can only be set once via append. A second append to an already-populated single-value attribute is an error naming the native alternative; append never overwrites. A buyer reading the phrase "Append value(s) to an object attribute" should not expect append to replace an existing single value
